## 1. The good news first

**Tiers 1 and 2 already exist and already fit.**

| v2 doc                 | Built today | Fit                                                                                                                                           |
| ---------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Tier 1 Superclass      | `field`     | Exact. Six rows seeded: thermoplastics, thermosets, elastomers, biopolymers, composites, high-performance                                     |
| Tier 2 Chemical Family | `family`    | Exact, **and it already nests** — `family.parent_id` is a self-reference, so Polyolefins → Polyethylenes is available today with no migration |

The property registry also survives untouched: 55 definitions, six groups, and
`applies_to_fields` was built precisely so a property can be scoped to the part
of the tree where it means something. The v2 doc makes populating it (gap G3)
much more urgent, but not harder.

---

## 2. Where it collides

**Tiers 3, 4 and 5 all collapse into `material` today, and Tier 6 collides with
`grade`.**

| v2 doc                     | Example                   | Built today                                         |
| -------------------------- | ------------------------- | --------------------------------------------------- |
| Tier 3 Main Polymer        | Polyethylene              | **does not exist** — PE is not a row anywhere       |
| Tier 4 Structural Sub-Type | LDPE                      | this is what `material` currently means             |
| Tier 5 Synthesis Variant   | Autoclave LDPE · C8-LLDPE | **no home**                                         |
| Tier 6 Processing Grade    | Cast Film Grade           | `grade` exists but means something else (see below) |

### 2a. `grade` means a product, not a processing class

`grade` is documented as _"A commercial product (e.g. Lupolen 2420H)"_ and hangs
off `organization`. The v2 doc's Tier 6 — "Cast Film Grade", "PE100 Pressure Pipe"
— is a **generic application class with its own textbook property ranges**, not a
producer's SKU. These are two different things and both are needed:

> Cast Film Grade LLDPE (generic, cited to handbooks) → Lupolen 2420H (a real
> product, cited to a manufacturer datasheet)

### 2b. Nothing inherits

The v2 doc's central mechanism is: _"parent nodes pass inherited traits down to
highly specific child nodes."_ `property_value` has no such concept. Every value
is attached to exactly one subject and resolves nowhere else.

## 3. Recommendation

**Add `material.parent_id`, exactly mirroring what `family` already does.**

Tiers 3, 4, 5 and 6 are not four different tables — they are **depth in one
self-referential chain**:

```
field: thermoplastics
 └ family: polyolefins
    └ family: polyethylenes          (family already nests)
       └ material: PE                 tier 3
          └ material: LDPE            tier 4
             └ material: Autoclave LDPE   tier 5
                └ material: Extrusion Coating Grade   tier 6
                   └ grade: "Lupolen 2420H"   ← the commercial product
```

The migration itself is small: one nullable self-FK and an index, the same shape
`family` already carries. **The schema is the easy part.** Three consequences are
not:

### 3a. Property resolution has to walk the chain

`v_material_properties` and `GET /api/materials/:slug` must resolve a value at
the nearest ancestor that defines it. A value on LDPE overrides PE's; where LDPE
is silent, PE's value shows through.

### 3b. This changes the value atom — the component everything is built on

Every value gains a state beyond sourced/unsourced: **specific to this node** vs
**inherited from an ancestor**. The reader must be able to tell "this density was
measured for Autoclave LDPE" from "this is the Polyethylene number, showing
through because nobody has narrowed it yet".

FE-2 is exactly the unit that builds this component, and FE-3 onwards is built
out of it. **Knowing this now saves a rewrite of every screen.** This is the
single strongest argument for settling the question before FE-2 starts.

### 3c. Inheritance makes the citation campaign survivable — this is the win

Six tiers × 55 properties × every branch of the v2 tree is an impossible amount
of manual citation. With inheritance it becomes tractable: **cite the density
range once at Polyethylene, and every descendant is covered until someone
narrows it.** Curation then only has to touch values that genuinely differ at a
given depth.

Without inheritance, the v2 taxonomy would multiply the curation backlog by the
size of the tree. With it, the tree mostly costs structure, not sources.

## 4. Two entities the v2 doc implies but does not name

### 4a. Concepts / topics

The owner's message lists what the learning environment will cover: surface
science, pigments, extenders and fillers, extrusion, rheology, analysis. **None
of these is a material.** They are concepts that many materials link to, and they
are precisely what makes Obsidian-style linking meaningful — without them the
graph is a tree with no cross-edges.

This wants a `topic` entity (or `concept`), linkable many-to-many with materials,
and it is what learning posts and article reviews attach to.

### 4b. Links as first-class data

"Obsidian link is the core" means a link is not an `<a href>` written in prose —
it is a row, so that **backlinks** work. A topic page must be able to answer
"which materials reference me?" That is a `link (from_type, from_id, to_type,
to_id, kind)` table, and it is what a graph view reads.

## 5. What this does to the frontend plan

- **L3 GRAPH stops being one of four concepts.** If Obsidian-style linking is the
  core, the graph is a candidate for the product's primary navigation, not a
  learning toy. That reopens D6 (homepage = browse + search as equals).
- **The datasheet gains a tail**: the owner's request — process as the last
  section, then buttons down to melt/tube/film grade — is a clean fit for the
  single-scroll datasheet (D23). Children are the natural end of the page, and
  "related topics" sit beside them.
- **FE-2 must be specified with inheritance in it**, per 3b.
- **"The whole thing is going to be a 3D website"** is unresolved and is the
  largest open risk to the performance budgets in `frontend-plan.md` §6 and to
  rule R24 (heavy libraries confined to Learn). See the questions below.

---

## 6. Questions — needed before FE-2, not before FE-1

1. **What does "3D website" mean?** Three very different answers: (a) a 3D graph
   view for navigation, like Obsidian's; (b) depth, parallax and dimensionality
   in an otherwise flat site; (c) genuine WebGL scenes as the primary interface.
   (a) is affordable and fits the Learn surface. (c) contradicts the mobile-first
   performance budget the owner set in round 2 (Q33) and would need that decision
   revisited deliberately.
2. **Is the graph the navigation, or a view?** Does a visitor arrive at a graph,
   or at a catalog with a graph available?
3. **Are concepts first-class?** Does "rheology" get its own page and its own
   link target, or is it only a learning post?
4. **Confirm the inheritance model** in §3 before FE-2 specifies the value atom.
5. **Confirm processing-grade vs commercial-grade** as two distinct levels (§2a).

Nothing here blocks FE-0 or FE-1. Questions 4 and 5 block FE-2.
